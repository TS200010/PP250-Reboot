# PP250 module addressing and Internal Mode

Status: research note, 28 September 2026. This note captures the current bottom-up reconstruction of System 250 addressing and the relationship of processor Internal Mode to that addressing. It should be read alongside `pp250-execution-and-process-model.md`.

## 1. Fundamental addressing model

**Documented basis / reconstruction:** System 250 should be modelled first as a collection of modules exposing addressable words. A processor forms an address consisting fundamentally of a **module selection plus an address within that module**.

The physical meaning of the addressed words is secondary to that addressing model. A module may implement ordinary store, peripheral/controller registers, or other system resources. Device registers can therefore be accessed with ordinary data operations because, from the processor's addressing point of view, they are addressed words in a module.

```text
             SYSTEM 250 ADDRESS
                    |
          +---------+---------+
          |                   |
       MODULE              ADDRESS
                             WITHIN
                             MODULE
          |                   |
          +---------+---------+
                    |
             addressed word
```

This is deliberately a hardware-level statement. It does not imply that all modules have identical behaviour, timing or access restrictions.

## 2. Capability address fields

A loaded capability contains the information required to define a bounded addressable region and the permitted operations on it. At the level relevant here the fields are:

```text
module + base-within-module + limit + access
```

Equivalently, where module selection and base-within-module are treated together as the capability's base address:

```text
base address + limit + access
```

An instruction using the capability supplies the relevant offset/modification; the processor constructs the effective reference and checks it against the capability's bounds and permitted access.

This note does not yet settle every bit position or version-dependent capability format. Those remain governed by the Pocket Reference, contemporary papers and patent evidence.

## 3. Each CPU has its own path to the modules

The multiprocessor topology must not be simplified into a single electrically common CPU bus. Each CPU has its own bus/path to the shared modules, with the Store Module access units and peripheral interconnection providing the shared-system topology.

Conceptually:

```text
 CPU 0 ---- CPU bus/path 0 ----+
                               +---- shared modules
 CPU 1 ---- CPU bus/path 1 ----+
```

Thus a normal module reference generated by a CPU is issued on that CPU's own system path toward the selected module.

## 4. Processor internal state is locally resolved

The processor's own internal state is the important special case.

The reserved all-ones module selection used for Internal Mode addressing should **not** be treated as the global module number of a particular physical processor. Instead, the current reconstruction is that the executing processor recognises this reserved module selection locally. The reference does not leave that processor on its system bus; the address within the reserved module selects addressable state inside the processor itself.

```text
instruction forms module + address
             |
             v
       inspect module
             |
      +------+------+
      |             |
 normal module   reserved internal
      |             module value
      v                 |
issue on this           v
CPU's bus/path      resolve locally
      |                 |
      v                 v
system module      this CPU's
                   internal state
```

This means that processor identity does not have to be encoded in the reserved internal-module address. The physical processor executing the instruction supplies that context.

## 5. Consequence in a multiprocessor system

**Strong inference from the local-resolution model:** the same internal-address reference denotes the internal state of whichever CPU is executing it.

```text
Process P executing on CPU 0:
    internal-module : offset -> CPU 0 internal state

Process P executing on CPU 1:
    internal-module : offset -> CPU 1 internal state
```

Consequently, this mechanism by itself does **not** let a process executing on CPU 0 address CPU 1's internal state. A process intended to collect global processor state would need to execute the relevant inspection on each CPU, or each CPU would need to export/report its state through ordinary shared system resources or some separately documented mechanism.

No separate mechanism for remotely addressing another CPU's internal registers is asserted here.

## 6. Internal Mode is a restriction, not a separate address space

This is the central clarification.

**Internal Mode does not create a second processor address space and should not be described as the mechanism that identifies a processor.** The processor already has locally addressable internal words selected through the reserved module-address interpretation.

Internal Mode is instead an **access restriction/condition governing access to that processor-local address space**. Possession of an address-forming capability is therefore not automatically equivalent to unrestricted access to every internal processor word; the documented Internal Mode rules and individual register restrictions still apply.

The conceptual distinction is:

```text
ADDRESSING:
    reserved module + internal word address
              |
              v
       this processor's word

ACCESS CONTROL:
    capability bounds/rights
          +
    Internal Mode restrictions
          +
    register-specific restrictions
              |
              v
       access allowed or rejected
```

The exact ordering of these checks in the hardware/microcode is not asserted by this diagram.

## 7. Evidence status and open checks

The following should be treated separately:

- **Documented:** System 250 uses per-CPU communication paths to shared modules; module/address information forms system references; peripherals expose addressable controller state; later Internal Mode material describes a reserved processor/internal-register module interpretation and restrictions on access to internal registers.
- **Strong reconstruction:** the reserved internal-module reference is intercepted and resolved by the processor executing the instruction, rather than naming a globally addressable processor module on the system bus.
- **Consequence of that reconstruction:** the same internal capability/reference follows the process to whichever CPU executes it and addresses that CPU's local internal state.
- **Not established:** a mechanism by which one CPU can directly address another CPU's internal-register address space. Do not invent such a path from the system diagrams.

## 8. Terminology correction for existing notes

Where existing research describes **"Internal Mode as a separate access mechanism"**, that wording should be read cautiously. The more precise current formulation is:

> **Internal Mode is an access restriction on locally resolved processor-internal addressing, not a separate physical address space or a globally addressed processor module.**

This distinction should be preserved in future emulator and architecture work unless primary evidence contradicts it.
